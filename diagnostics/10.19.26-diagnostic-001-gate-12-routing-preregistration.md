## Research question

In this group chat, does the *visible 60-second reply rate* differ among (A) explicitly addressed new tasks, (B) clear immediate follow-ups to the assistant's most recent message, and (C) unaddressed standalone new tasks? Does task correctness differ conditional on receiving a reply?

## Competing hypotheses (not observations)

- H1: A and B will receive more visible replies than C because group-chat addressing/continuity eligibility differs.
- H0 (descriptive null): No consistent visible reply-rate difference will be observed in this small sample.
- Alternative explanations: conversational adjacency, task clarity, setup effects, UI/client delivery, other participants, and stochastic behavior. No result will establish internal routing mechanism without platform logs.

## Conditions and prescored eligibility

- **A — Direct address (eligible):** Prompt starts `ChatGPT,` and specifies a two-word code to reverse.
- **B — Clear follow-up (eligible only if setup succeeds):** An explicitly addressed setup first elicits the exact two-word code from the assistant. The user then asks to reverse the code in the assistant's *immediately preceding message*, without saying ChatGPT. No intervening messages; aim to send within 30 seconds of the setup reply. If adjacency or timing fails, flag confounded, not silently discarded.
- **C — Unaddressed standalone (ineligible under original D001 rules):** Same standalone transformation as A, but omits `ChatGPT,` and does not reference the previous assistant message. This condition tests user-experienced silence, **not** a protocol-defined assistant failure.

## Locked design

Six blocks, one A, B, and C probe per block: **18 probes total, six per condition**. The order is precommitted to all six permutations, balancing first/second/third position across conditions. Codes are held constant within a block, varied between blocks. Do not re-order after observing outcomes.

### Exact prompt templates (substitute only the code from the table)

The A and C prompts differ only by direct address. B necessarily differs by using prior context; treat that as a structural confound, not an equivalence claim. Setup messages are logged separately from the 18 probes.

## Procedure

1. Use the current group chat. Before each probe, record its condition, code, expected answer, and whether it meets the prespecified eligibility rule. No tool calls, web questions, or other tasks in probes.
2. Send probes in the block order above. For B, first send its setup; require the assistant to visibly return the exact code. If the setup receives no timely correct reply, record `setup_failed`, mark the B probe `not_launched`, and continue without inventing or replacing an observation.
3. For each launched probe, note the visible UTC user-message timestamp. Observe for **60 seconds**; do not send reminders or another probe during that window, even if the reply arrives early. If a reply is late, log its actual timestamp separately.
4. For B, after a successful setup reply, send the follow-up without an intervening message, preferably within 30 seconds. Record any delay beyond 30 seconds as a timing confound. The setup-to-probe interval is distinct from the probe's own 60-second observation window.
5. Log other participants' messages, overlap, tool behavior, UI uncertainty, and connectivity concerns as confounders. Preserve every scheduled block and every failed setup in the final report.
6. Do not send a reminder until after the 60-second window. Any reminder and later reply are separate events; they never retroactively change the primary 60-second outcome.
