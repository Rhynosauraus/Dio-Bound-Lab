## Packaging boundary
The Portable Core is ONE upstream normative source, not one fork per project. Consumers may have minimal local *adapters*, but may not silently modify the upstream rules. A shared instruction can be copied into a thread or project **only after** the relevant owner has admitted its version, scope and permissions. A repository link, chat message, branch or merged PR is not a live worker installation.

### Release sequence
1. **Candidate:** review this branch, compare with original v0.1 user charter and DIO history, retain corrections to PE-FRAME-001.
2. **Source acceptance:** after human approval, give the exact released commit SHA, file hashes and version to every consumer. Do not rely on floating main links.
3. **Sandbox pilots:** first run controlled synthetic/manual uses; compare engine decision value against a simple baseline. Do not distribute sealed PE-BENCH-001 reference keys to candidates.
4. **Adapter-specific qualification:** prove the target actually received the exact payload, respected its local evidence boundaries, and did not acquire authority.
5. **Opt-in expansion:** introduce one destination at a time, with documented rollback and consumer registry; stop on semantic drift, missing receipts, or new grants.
6. **Version retirement:** keep historical pins and receipts; explicitly approve upgrade and migration. Never silently overwrite a consumer's governing text.

### Source identity
Required distribution record: package_version; exact Git commit SHA; exact path and SHA-256 of each transmitted file; recipient/project identifier; intended question or scope; permitted operations; approval source; transport mechanism; sent/received/adopted state; timestamp; reviewer; and rollback/refusal instructions. Record **UNKNOWN**, not DELIVERY_CONFIRMED, if no supported independent readback exists.

### Mandatory negative trials
- **Proposition switch:** a stage answers an easier question, not the exact input → BLOCK.
- **Ghost source:** a cited source ID is absent or fabricated → BLOCK.
- **False independence:** same model stages claim to be separate confirmations → BLOCK.
- **Authority escalation:** build recommendation represented as human approval or new grant → BLOCK.
- **Forecast laundering:** predictions relabeled as observed outcomes → BLOCK.
- **Framing interference:** accusatory/absurd framing changes conclusion despite same evidence → investigate; no automatic fail without independent adjudication.
- **Version mismatch:** stale/unpinned core presented as current → BLOCK distribution.
- **Wrong destination or missing receipt:** sender claims successful live adoption without independent readback → mark UNKNOWN; no blind retry.
- **Sealed benchmark leakage:** reference keys appear in candidate instructions → INVALID TEST.
