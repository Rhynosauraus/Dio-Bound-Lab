## 2. Proposed A0 commitment proof

**Challenge source:** D, outside the gateway's write authority, must create and durably retain a unique unpredictable nonce (minimum 128 bits) bound to its own intended effect context and current independent checkpoint. This source packet **does not generate, protect, consume across processes, or store any nonce**.

**A0 signed response schema:** `schema`, `authority_id`, `proof_status`, `root_id`, `key_id`, `generation`, `activation_epoch`, `registry_digest`, `reservation_id`, `reservation_payload_sha256`, `reservation_commit_sequence`, `a0_head_sequence`, `checkpoint_digest`, `challenge_nonce`, `run_id`, `episode_id`, `action_id`, `grant_id`. A0's commitment response is intended to be signed by an independently pinned authority verification key.

**Strict byte proof:** ASCII canonical JSON with sorted keys, compact separators and exact 4096-byte maximum; reject duplicate fields, extra/missing fields, bool-as-integer, invalid IDs/digests and impossible local sequence regression. The prospective Ed25519 signature input contains a domain-separated prefix, four-byte payload length, and exact canonical bytes. The root/key identity and SHA-256 of the exact 32-byte public key must match an **independently enrolled T0 fingerprint**, never a registry value supplied by a request.

**D verification:** The signed proof must match D-owned run/episode/action/grant, root/generation/epoch/registry, reservation ID/commit sequence/raw payload digest, checkpoint digest and one-time challenge nonce. The resulting proof object may only be used by a D-controlled adapter that checks the original expected reservation and does not allow the gateway to substitute verification callbacks or expectations.

**Effect claim:** This v0.4 object is not itself an effect counter. The intended future integration is: authenticate A0 reservation envelope v0.2 → check independently pinned A0 commitment proof v0.4 → D one-use effect claim v0.3 → D grant/generation/global STOP fence and effect commit in the same durable transaction. Real ownership, atomicity, and current revocation state are not established here.

## 3. Adversarial source-only tests and deliberate failure cases

**26** source test functions AP01–AP26 correspond one-to-one with JSON case entries. All are `NOT_RUN`. They cover correct test-only proof, different challenge nonce, old generation/epoch, wrong checkpoint, altered reservation, invalid signature, substituted key, invalid JSON and numeric types, provider failure, one-shot adapter consumption and cross-run binding.

**AP21 and AP26 — stale checkpoint:** An otherwise valid signed proof may remain historically authentic after an independently managed checkpoint changes. This model cannot discover unobserved advancement by merely checking a cached checkpoint digest. A deployed D must independently obtain the current external authority high-watermark, and effect-time generation/grant/STOP rules must remain valid.

**AP22 — compromised verifier callback:** The adapter accepts a deliberately fabricated success result when a caller supplies a dishonest proof-verification function. **This is a known, intentional model vulnerability** demonstrating that Python dependency injection cannot enforce D-owned configuration or independent key custody.

**AP25 — reuse of same nonce via a second instance:** Two one-shot adapter instances can each accept the same valid proof. The word "one-shot" describes a local object, not a globally durable nonce-consumption ledger. A real D requires atomic durable challenge issuance/consumption or equivalent replay-bound authorization, independently witnessed.

**Test-only cryptography:** Tests use a deterministic SHA-512 fixture comparison named `TEST_ONLY_NotEd25519`, which is NOT Ed25519, not a valid signing scheme and not suitable for runtime trust. The optional future `cryptography` Ed25519 provider is defined in source only; no dependency was installed, imported or qualified, and no keys generated.
