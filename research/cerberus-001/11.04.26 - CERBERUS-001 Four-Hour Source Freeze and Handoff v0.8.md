## Final narrow semantic finding: exact-class but damaged ReadIntent

At v0.7, `record_d_private_read_attempt()` checks `type(intent) is ReadIntent`, then directly reads `intent.original_token_bytes`, `intent.reservation_id_claim`, `intent.principal_id_claim`, `intent.receipt_grant_id_claim` and `intent.original_issuer_key_id_claim`, **before appending an attempt row**. An exact-class Python dataclass instance whose required attribute is absent (possible via malformed in-process construction, deserialization boundaries or reflection) can raise on attribute access. The current source has no local `AttributeError`/missing-field fallback around those reads.

**Author source-semantic disposition:** **BLOCK** for any broad claim that v0.7 always records every malformed `ReadIntent` supplied alongside a valid model journal. This is a reasoned source inspection, not a test run or proven external exploit; legitimate real D inputs must be admitted only through a protected validated decoder. The narrow case is **FZ01** in the accompanying `11.04.26 - CERBERUS-001 Independent D2 Acceptance Challenges v0.8.json`. An independent D1 reviewer should classify severity and either produce a minimal versioned source guard or preserve a clearly scoped exclusion. **Do not silently change v0.7** to erase the record.

This finding does not make source-level input hardening a substitute for D custody. Even a fully guarded in-memory journal still cannot certify durable observation of every arrival, retries across process restart, external response delivery or requester authorization.
