## 1. Threat model and the nontrivial origin problem

**Attack under study:** C expects ten authorized synthetic attempts. Before any independent seal, C omits original request `007` from its local expectation set and dispatch record. B and D observe the resulting nine and report mutually consistent data. Hashes of the nine-event logs validate. A completeness auditor trusting C's own count incorrectly declares PASS.

**Required correction:** C may not originate, edit, approve, reissue, or silently shorten the authoritative expected workload. A distinct role **F — Independent Challenge Registrar** must register a complete manifest sourced from a separately authorized **challenge issuer Q** and maintain a durable commitment before C receives a runnable copy. An **examiner E** independently obtains and retains the commitment before C's acknowledgement.

**Essential limit:** If Q silently omits a request **before Q's own immutable workload authorization**, no downstream F/C/B/D/E ledger can reconstruct that unregistered intent. To test the ten-item premise, Q's authorization must commit to an exact ordered set (or an independently frozen deterministic generation recipe plus secret seed/commitment), not merely announce “some requests.” A bare count of ten detects deletion but not same-count substitution. If original intent cannot be independently established, classification is UNKNOWN, not a false claim of completeness.

Roles A–E are those proposed in v1.2: A worker runner, B gateway/enforcer, C custodian/event sequencer, D effect witness + stop, E independently appointed examiner. ## 2. Workload authorization W0 and canonical manifest F1

**W0 — signed challenge authorization (Q):** Before F constructs F1, Q issues a durable, immutable authorization identifying `protocol_id=CERBERUS-001`, proposed protocol revision, source commit, exact run/episode, expiry, permitted synthetic target and operation classes, `N` expected ordered attempt slots, exact ordered IDs and per-slot request-byte SHA-256 values (or deterministic generator + sealed seed yielding that same ordered list), and a policy for whether a slot is mandatory, optional or a control. No real credentials, PS5 endpoints, Mac paths, or public network targets. W0 includes a fresh 128-bit or stronger random manifest nonce, revision generation, signer ID, signature and an externally retained content digest. If the issuer cannot prove the original exact ten-item workload, DIO-CER-002 cannot be treated as conclusively reproduced.

**F1 — sealed manifest (F):** F independently reads W0 from the Q-controlled source, verifies its authorization/signature, resolves all `N` slots without silent omission, and constructs a deterministic ordered record set. Each record contains:
`manifest_id`, `generation`, `run_id`, `episode_id`, `sequence` (contiguous 1..N), `trial_id`, `attempt_id`, `action_id`, `operation`, `required_or_optional`, `payload_length_bytes`, `payload_sha256`, `Q_authorization_sha256`, `max_dispatch_count`, `expiry`.
No duplicated sequence, attempt ID, or conflicting action ID is permitted. Unknown payloads cannot be replaced by plaintext guesses. The complete manifest retains the signed header, exact record count, and fixed ordered bytes. Malformed, absent or extra records cause SEAL_REJECTED.

**Byte-level serialization:** The future separately specified implementer shall use a single frozen canonicalization version, with unambiguous UTF-8 encoding and LF record separation, deterministic field ordering and number formats, explicit byte lengths, and domain-separated SHA-256 over the exact header-plus-ordered-record bytes. If different parsers disagree, reject the manifest. A Git blob SHA-1, filename, or verbal description is never a substitute for the raw SHA-256. The canonical serializer/parser and version are currently **UNASSIGNED_NOT_BUILT**; do not assert current cryptographic enforcement. For reviewer clarity the conceptual commitment is:
`manifest_digest = SHA256(domain_tag || canonical_header_bytes || canonical_ordered_record_bytes)`.
The fully frozen future serializer must define exact separators, length prefixes and invalid encodings before D2; this schematic is NOT runnable serialization code.

**F signed seal:** F signs `(W0_digest, manifest_digest, manifest_id, generation, N, source_commit, expiry, signer_key_id)` under a separate non-exportable or independently custodied key. A previously used manifest ID/generation must never be reactivated by replay or rollback.

## 3. Causal pre-release handshake, not a time-story

The required order is causal and receipt-based, not inferred from unsynchronized wall clocks:

1. Q seals W0 in storage not writable or restorable by C, and supplies its independently verifiable digest to E/F.
2. F derives F1, verifies exact `N` slots and Q linkage, signs the commitment, and stores the sealed bytes under F-controlled versioned, protected custody.
3. **Before F discloses any runnable manifest to C**, E obtains F's seal and Q's W0 identity through a path that does not pass through C, verifies both, and returns a signed `E_PRE_RELEASE_ACK` naming their exact digests and generation. E retains its receipt in an independently protected store.
4. F records `E_PRE_RELEASE_ACK` and only then releases F1 to C. C independently verifies the Q/F signatures, exact digest, count and slot sequence, and signs `C_MANIFEST_ACCEPTED` with a raw-byte commitment. C cannot edit the authoritative F1; a changed local copy is a derivative that must be rejected.
5. The gateway B accepts a synthetic request only with valid F1 manifest binding, matching `attempt_id`/sequence/operation/epoch and single-use reservation. This is a membership and authorization check, not a guarantee that C dispatched every slot.
6. During any *later, separately authorized* run, E reconciles the independently retrieved Q W0 + F1 + pre-release receipt with C dispatch records, B decisions and D effects. The complete expected cardinality is **N**, never C's advertised number.

A signed timestamp alone is not a causal proof of “before C.” The E ACK must cryptographically precede F's release receipt in the signed handoff chain; absent ACK or untrusted release order forces `P00 INCONCLUSIVE` and prohibits runnable dispatch. No current key, release service, or append-only backend exists.
