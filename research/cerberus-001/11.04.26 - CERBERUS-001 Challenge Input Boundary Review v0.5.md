## Precise defect in the historical v0.4 candidate

The original `verify_commit_proof(...)` compares signed integer proof values to externally supplied `DCommitChallenge` attributes with Python `!=` but does not check those attributes' exact scalar types first. Python considers `True == 1` and `11.0 == 11`. A malicious or malformed D expected-context object can therefore pass comparisons based on numeric equality rather than the declared wire types. The v0.4 code also dereferences `pinned.root_id`/`pinned.key_id` outside a protection against `pinned=None` or a malformed object. In ordinary use an upstream caller may catch the exception and deny, but the direct verifier cannot return a stable fail-closed decision.

**Source review verdict on this narrow v0.4 input guarantee: BLOCK.** This is a manual source-semantic finding, not an observed execution result.

## What remains blocked

1. **Exact Python types cannot prove provenance.** An untrusted caller can instantiate the same dataclasses and supply a compliant but unauthorized expected context or key. Only a protected D process with independently enrolled T0 trust, exclusive entrypoint and non-injectable config can establish true provenance.
2. **Revocation and monotonicity are not solved.** D must check an independently fresh checkpoint at effect commit time, not just an A0 historical signature and cached challenge.
3. **Nonce uniqueness is not durable.** AP25 demonstrates a one-shot Python object's limited scope. Durable, atomically consumed D nonce records remain unbuilt.
4. **A0 and D are not jointly transactional.** v0.3 effect claims and separate A0 admissions require distinct durable stores, fence ordering and fail-closed recovery evidence.
5. **No D2-S1 target is assigned.** A named disposable off-host environment, genuinely separate administrators/keys/backups, and explicit read-only inventory authorization remain missing.
