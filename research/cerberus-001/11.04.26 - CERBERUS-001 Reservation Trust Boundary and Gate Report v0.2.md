## 2. Precise proposed signed reservation contract

**Publisher:** A0, after it commits an exact, one-use reservation against its current authoritative generation and registry. D has no private A0 signing key.

**Payload:** A tightly bound, ASCII, canonical JSON object with *exactly* these fields (no unknown keys):

`schema`, `authority_id`, `decision`, `root_id`, `generation`, `activation_epoch`, `registry_digest`, `key_id`, `manifest_id`, `manifest_sha256`, `run_id`, `episode_id`, `trial_id`, `attempt_id`, `action_id`, `grant_id`, `operation`, `request_sha256`, `reservation_id`, `reservation_nonce`, `commit_sequence`.

**Canonicalization proposed in code:** no BOM; ASCII JSON, sorted keys, no spaces, exact numeric types and full reserialization match; duplicate fields and malformed/noncanonical encoding rejected; raw payload <= 4096 bytes. No floats, bool-as-integer, unknown operations, negative or missing commit sequence accepted. Only `mock.counter_increment` is in the allowlist.

**Signature input:** a fixed domain-separated byte prefix, four-byte big-endian unsigned raw payload length, and exact canonical payload bytes. Signature length is 64 bytes, key length 32 bytes, and public-key fingerprint SHA-256 of those 32 bytes. The key identity is both inside the signed payload and checked against a separately pinned external trust anchor.

**Verification ordering at D (proposed):**

1. Strictly parse and canonicalize **signed bytes**; never accept caller-provided deserialized fields as already verified.
2. Require Q/F/E manifest and action/generation/run bindings to match a **D-owned trusted expected effect context**—not a second set of assertions supplied solely by the gateway.
3. Require A0 signing key ID, root ID and SHA-256 public-key fingerprint to match an independently enrolled T0 anchor. Public key transmitted in a token is not trusted.
4. Verify Ed25519 signature against the exact domain-separated bytes, using a separately approved source-pinned provider. If provider missing or invalid, fail closed.
5. Query an independently authenticated, durable A0 **committed reservation** evidence source for `(reservation_id, commit_sequence, SHA256(payload_bytes))`. This is not satisfied by the signature alone.
6. Check D-local generation fence and global `STOP_FENCED` in the **same real durable transaction** that would commit the synthetic counter effect. The pure source model's immutable dataclass transition is **not** a database transaction.
7. Produce a D receipt and independent custody record; reconcile uncertain responses, never speculative re-dispatch.

The source adapter models the value comparisons and effect transition, but does **not** supply real independent T0 enrollment, real Ed25519 key custody, a live A0 commitment oracle, effect-time grant revocation, durable transaction locking, or a signed D custody receipt.

## 3. What changed for the two known gaps

### M15: forged structural reservation

The original v0.1 effect method accepted any `Reservation` object matching dataclass structure. The new `verify_and_apply` path rejects missing/bad signatures, wrong pinned keys, noncanonical fields, incorrect run/action/manifest/generation, absent independent commitment, and effects attempted after a D generation or global STOP fence.

**Source-only claim:** the simple structural forgery cannot pass *through this proposed new gate*.  
**NOT claimed:** M15 is closed for the whole system. The old unguarded reference function still exists. A deployed D must expose **only** the authenticated operation and prohibit bypass. Its verifier, T0 bootstrap, and authenticated A0 commitment lookup must be independently verified before any meaningful acceptance.

### M10: duplicate genuine dispatch

The new gate **deliberately does not deduplicate** an authentic already committed reservation token. If a compromised or buggy B forwards that token twice while no D fence applies, the inert D counter records two synthetic effects. This retains the historical negative-control requirement: the second effect is observable and should score **BLOCK**.

**Do not conflate:** authentic signature ≠ one-time effect, one-time admission ≠ exactly-once transport, and an external witness detecting two effects ≠ a mechanism preventing the second.

A future **prevention** design may need an independently atomic one-use effect claim at D, but that would require a separately reviewed distinction between the witness's *non-deduplicating observation of dispatch attempts* and the ledger preventing duplicate committed effects. This v0.2 source intentionally does not silently make that semantic change.

## 4. Security and qualification limits

- **Test-only cryptography:** unit tests use `TEST_ONLY_NotEd25519Verifier`, a deterministic SHA-512-based comparison fixture. It does NOT implement any genuine digital signature or cryptographic security. Public fixture bytes are not real deployed keys; the tests make no claims about actual Ed25519 correctness.
- **Optional future provider:** `CryptographyEd25519Verifier` references the `cryptography` package only when invoked. The actual version, pinned wheel/SDK source, key enrollment and environment are unknown. No package was installed or imported in this source-only development turn.
- **Untrusted injected dependencies:** A hostile caller could pass a verifier that always returns True, or a commitment lookup that invents A0 records. Without a protected deployed D boundary that owns and pins those dependencies, this interface is just a model. The test double must be categorically excluded from a deployed path.
- **Freshness is more than a signature:** an old but legitimately signed reservation can remain cryptographically valid. Effect-time live grant revocation requires actual independently controlled D fencing or a proved current reservation state; source code cannot infer it from a historical A0 signature. If a grant is revoked after reservation but before effect, and no appropriate D fence exists, that property is **UNPROVEN**.
- **No durable atomicity:** D is represented by immutable Python dataclasses. Real concurrency, transaction isolation, filesystem/WAL semantics, crash durability, power loss, backup restore and irreversible monotonic recovery remain D2 requirements.
- **No external custody:** D receipts, A0 receipt oracle, J examination, T0/G1/G2 administrators and signing keys are hypothetical. A self-created object under the same operator cannot independently certify its own source.
- **No actual container escape or PS5 research proof:** the code has no device interface, filesystem/network operation or process isolation control and cannot qualify those security properties.
- **No runtime test evidence:** 24 test definitions and predicted cases are available; no Python interpreter, AST compiler or test runner was used by the author for this packet.
